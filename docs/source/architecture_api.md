# 2 Архитектура и API

Сохраняется сервисная декомпозиция ЛР 3 с общей реляционной моделью и слоем доступа к данным. Клиенты используют API Gateway. Эта итерация не вводит отдельные базы микросервисов или брокер сообщений.

## Диаграммы из ЛР 4

Сохранены исходные диаграммы взаимодействующих компонентов и платёжного фасада. Новые операции заказов расширяют их контракты; состав компонентов не меняется.

## Паттерн Фасад

PaymentFacade предоставляет createPayment, getPayment, listPayments, cancelPayment и внутренний recordConfirmedResult. PaymentRepository отвечает за транзакционные записи и устойчивые ключи. PaymentProviderClient регистрирует, проверяет и отменяет внешние операции. PaymentResultDelivery выполняет фоновые HTTP-уведомления и повторы. Компонент заказов проверяет владельца и выбранный отклик; сумма определяется по responses.price.

## Общие правила контракта

Базовый путь /api/v1; HTTPS, JSON UTF-8. Все запросы содержат Bearer-токен и X-Request-Id. Для тела JSON требуется application/json. Идентификаторы — положительные целые, денежные суммы — строки с двумя знаками после точки, валюта BYN, время UTC ISO 8601. На каждой операции проверяются роль и принадлежность объекта. Служебный токен проверяется по сроку, аудитории, сервису и правам payments:create/read/cancel либо orders:payment-events.

| Метод | Путь после /api/v1 | Назначение | Успех |

| --- | --- | --- | --- |

| POST | /payments | Создать платёж | 201, 200 |

| GET | /payments | Список платежей заказа | 200 |

| GET | /payments/{payment_id} | Получить платёж | 200 |

| POST | /payments/{payment_id}/cancel | Отменить ожидающий платёж | 200 |

| POST | /orders/{order_id}/payment-events | Принять результат оплаты | 204 |

| POST | /orders/{order_id}/cancel | Отменить свой заказ с причиной | 200 |

| POST | /orders/{order_id}/work-completion | Сообщить о выполнении | 200 |

| POST | /orders/{order_id}/completion-confirmation | Подтвердить завершение работ | 200 |

| POST | /orders/{order_id}/payment-attempts | Начать или повторить попытку оплаты | 201, 200 |

| GET | /orders/{order_id}/payment-attempts | Посмотреть свои попытки оплаты | 200 |

| GET | /orders/{order_id}/payment-attempts/{payment_id} | Посмотреть состояние своей попытки | 200 |

## Операции и условия выполнения

## POST /payments

Заказы -> платежи. payments:create. Тот же ключ и тело возвращают прежний платёж; другое тело под тем же ключом даёт 409. Одновременные pending и succeeded по одному заказу запрещены. Намерение сохраняется до обращения к провайдеру. При неопределённом исходе 503, состояние pending.

Схема тела: CreatePayment. Полный контракт, обязательные поля и ограничения приведены в docs/source/openapi.yaml.

## GET /payments

payments:read. Сортировка created_at DESC, payment_id DESC. total считается после фильтрации до пагинации. При отсутствии результатов items=[], total=0.

## GET /payments/{payment_id}

payments:read. Возвращает последний сохранённый статус. failed в теле не меняет успешный HTTP-код чтения 200.

## POST /payments/{payment_id}/cancel

payments:cancel. Без тела. canceled устанавливается только после подтверждения провайдера. Повтор отменённого платежа — 200. succeeded и failed — 409. При неопределённости 503 и pending. Отмена платежа не меняет состояние заказа.

## POST /orders/{order_id}/payment-events

Платежи -> заказы, orders:payment-events. order_id пути и тела совпадают. Проверяются платёж, заказ, сумма и валюта. Повтор event_id с теми же данными — 204 без второго эффекта; другой состав данных или противоречивый конечный статус — 409. Событие сохраняется атомарно с локальным представлением результата.

Схема тела: PaymentEvent. Полный контракт, обязательные поля и ограничения приведены в docs/source/openapi.yaml.

## POST /orders/{order_id}/cancel

FB-01. Только владелец и только draft/published. reason обрезается по краям и проверяется на 5–500 символов. Статус и история с причиной фиксируются одной транзакцией. Повтор canceled с той же причиной — 200 без новой истории; иная причина — 409. После assigned обычная отмена запрещена.

Схема тела: CancelOrder. Полный контракт, обязательные поля и ограничения приведены в docs/source/openapi.yaml.

## POST /orders/{order_id}/work-completion

FB-03. Только выбранный исполнитель. in_progress -> awaiting_confirmation. Без тела. Повтор уже достигнутого состояния — 200 без второй истории; любое иное исходное состояние — 409.

## POST /orders/{order_id}/completion-confirmation

FB-03. Только владелец. awaiting_confirmation -> completed; после перехода разрешён отзыв. Без тела. Повтор completed — 200 без второй истории; иной исходный статус — 409.

## POST /orders/{order_id}/payment-attempts

FB-02. Пользовательский Bearer, только владелец. Тело {}. Заказы определяют customer_id и сумму по выбранному отклику; клиент их не передаёт. Оплата разрешена после выбора исполнителя и до/после выполнения, кроме canceled. Компонент заказов вызывает внутренний POST /payments со служебным токеном и тем же ключом. При pending новый ключ запрещён; после failed/canceled нужна явная новая попытка и новый ключ. После succeeded новый платёж запрещён.

Схема тела: EmptyRequest. Полный контракт, обязательные поля и ограничения приведены в docs/source/openapi.yaml.

## GET /orders/{order_id}/payment-attempts

FB-02. Только владелец заказа. order_id берётся из пути; ответ ограничен этим заказом. page/page_size/status и сортировка как у внутреннего списка.

## GET /orders/{order_id}/payment-attempts/{payment_id}

FB-02. Только владелец; payment_id обязан принадлежать order_id. При несовпадении принадлежности операция отклоняется. Возврат из браузера провайдера не меняет статус.

## Идемпотентность и доставка

Ключ Idempotency-Key содержит 8–64 латинские буквы, цифры, дефис или подчёркивание. Ключ хранится в области вызывающего компонента и операции вместе с хешем нормализованного запроса и payment_id. Повтор с другим телом даёт 409. Срок удаления ключа в этой редакции не установлен; до введения политики очистки записи сохраняются. Регистрация намерения и ключа выполняется до вызова провайдера.

Подтверждённый результат и задание его доставки с event_id сохраняются одной транзакцией. Доставка и фоновая сверка используют исходные ключи. Получатель записывает event_id и содержимое результата атомарно; повтор не вызывает повторный эффект. При конфликте результат направляется на сверку, а не перезаписывается. Обработчики ограничивают повторы и увеличивают паузу; неустранённые задания остаются в хранилище и журнале.

## Состояния и ошибки

pending означает отсутствие подтверждённого результата. Из pending допустим единственный переход в succeeded, failed или canceled. Сетевая ошибка не означает failed. Статус платежа независим от состояния выполнения заказа. HTTP 200 при GET означает успешное чтение даже при status=failed.

| HTTP | Смысл |

| --- | --- |

| 400 | Некорректный JSON, путь или заголовок |

| 401 / 403 | Нет аутентификации / необходимых прав |

| 404 | Платёж или заказ не найден |

| 409 | Конфликт состояния, ключа или события |

| 415 / 422 | Неверный тип тела / нарушение ограничений |

| 500 / 503 | Внутренняя ошибка / временный сбой с возможной неопределённостью исхода |

## Схемы данных

Payment: payment_id, order_id, customer_id, amount, currency, status, external_op_id, confirmation_url, created_at.

CreatePayment: order_id, customer_id, amount, currency.

PaymentEvent: event_id, payment_id, order_id, amount, currency, status, occurred_at.

PaymentList: items, page, page_size, total.

CancelOrder: reason.

EmptyRequest: пустой объект.

OrderState: order_id, status, changed_at.

Error: error.
